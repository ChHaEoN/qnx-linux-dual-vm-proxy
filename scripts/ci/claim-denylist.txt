# claim-denylist.txt -- claim strings this repository does not support.
#
# Format, one rule per line:
#     <regex>  <TAB or two+ spaces>  <why this claim is not supported>
# A line beginning with '!' is an EXEMPTION instead: a sentence no rule may fire
# on, with the reason it was inspected and cleared. Blank lines and '#' comments
# are ignored. Extend this file freely; no Python change is needed.
#
# HOW A RULE FIRES. scripts/ci/claims_gate.py splits prose into SENTENCES (not
# lines -- the docs wrap) and reports a match only when the sentence is an
# ASSERTION. A sentence carrying a negation ("no", "not", "never",
# strike-through) or a planned-marking ("design intent", "never built",
# "superseded") is not a violation.
#
# That exemption is load-bearing, not a loophole. This project's honest framing
# requires sentences like "Nothing in it is certified" and "No certified Type-1
# isolation" -- a naive substring denylist would fail the build for exactly the
# text that makes the README truthful. Verified 2026-09-19: all 2 ASIL, all 10
# "certified" and all 4 "Graviton" sentences in README.md classify as negated or
# planned, and none as asserted.
#
# A RULE CAN OUTLIVE ITS PREMISE, and then it bans the evidence instead of the
# lie. That has now happened twice in this file -- see the acceleration and
# Graviton sections. When a rule is narrowed, the reason is written down here
# with its date, and both directions are pinned in tests/test_prose_gate.py.

# --- acceleration. REWRITTEN 2026-09-20; the reason matters more than the rules.
# The three rules that used to live here banned any claim that a measurement was
# taken under KVM. They were written before any run had been taken with QNX as a
# KVM guest, so every such sentence was false by construction. That premise
# ended twice:
#   2026-09-19  guest latency runs with QNX as a KVM guest, governor pinned
#   2026-09-20  boot-timing runs under KVM on two hosts, byte-identical image
# (their results are held locally, NC QDL v7 4.6(i)). Keeping the blanket ban
# would have banned true statements of what was done. What is STILL universally
# false is narrower and is what these rules now protect:
#   * a hardware-timed HYPERVISOR number. The QNX Hypervisor cannot run under
#     KVM at all -- it needs EL2 and ARM KVM does not nest on A78AE -- and no
#     figure from the native (A4) leg is published.
#   * that the A1-A3 legs were KVM-accelerated. Every one ran TCG.
\bhardware[- ]timed\b[^.]{0,60}\b(hypervisor|QHV|qvm)\b	no hardware-timed hypervisor number exists anywhere; QHV needs EL2 and ARM KVM does not nest on A78AE
\b(A1|A2|A3|cloud leg|Orin plain leg)\b[^.]{0,70}\b(under|on|with)\s+KVM\b	the A1-A3 legs all ran under TCG, not KVM
\bKVM[- ]accelerated\b[^.]{0,40}\b(A1|A2|A3|cloud|twin diff|IPC)\b	no KVM-accelerated figure exists for those legs; they are TCG

# --- the cloud LEG. Still never built, and that is separate from the boot arms.
# AWS has been used several times (a t4g.small /dev/kvm probe, a1.metal KVM
# boot captures, the 2026-09-20 twin boot measurement, and A6 ladder and harness
# sessions on a1.metal from 2026-09-21; every record is held locally), so
# "nothing ran on AWS" is false. What does not exist is a cloud LEG in this
# project's sense: a QHV host plus guest running the IPC benchmark.
#
# 2026-09-22: these two rules said "the only cloud measurement is boot timing"
# for a day after the a1.metal ladder ran (20260921T-ladder-a1metal), and three
# documents repeated it. The rules stay, because every OTHER cloud IPC claim is
# still unsupported. Later the same day the Orin's notified-shm ladder ran on
# a1.metal too (20260922T-a6-a1metal-kick): TCP, the D-udp rung, polled and
# notified shared memory. The exemption below clears a1.metal sentences about
# those ladders and paths from these two rules ONLY (it is scoped {cloud-ipc}),
# and never one that names throughput or another cloud host.

# Keyed on the HOST token, never on the word "cloud": "cloud leg" is this
# project's NAME for architecture A1, which ran on the local Windows PC, so
# banning "cloud" near "IPC" would ban the project's own vocabulary.
\b(Graviton|AWS|EC2|a1\.metal|c7g|t4g)\b[^.]{0,80}\b(IPC|latenc\w*|throughput|p50|p99|benchmark\w*)\b	[cloud-ipc] the only cloud IPC/latency runs are A6's on a1.metal (ladders from 2026-09-21, later harness sessions; records held locally); no throughput run, and none on any other cloud host
\b(IPC|latenc\w*|throughput|p50|p99|benchmark\w*)\b[^.]{0,80}\b(Graviton|AWS|EC2|a1\.metal|c7g|t4g)\b	[cloud-ipc] the only cloud IPC/latency runs are A6's on a1.metal (ladders from 2026-09-21, later harness sessions; records held locally); no throughput run, and none on any other cloud host
!{cloud-ipc}(?:^|(?<=\n))(?![^\n]*\b(throughput|bandwidth|[GMK]i?B/s|[GM]bit/s|msg/s|messages per second)\b)(?![^\n]*\b(c7g|t4g|Graviton[23]|non-metal)\b)(?=[^\n]*\ba1\.metal\b)[^\n]*\b(ladders?|UDP|shared[- ]memory|shm|doorbell)\b	A6 ladders did run on a1.metal: TCP on 2026-09-21 (20260921T-ladder-a1metal); TCP, the D-udp rung, polled and notified shared memory on 2026-09-22 (20260922T-a6-a1metal-kick). Scoped to the cloud-ipc rules only; never cleared when throughput or another cloud host is named
